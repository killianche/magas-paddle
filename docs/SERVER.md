## Переезд на домен клуба (03.10.2026)

Домен `padelmagas.ru` зарегистрирован клубом в reg.ru, записи A на `@` и `www`
указывают на `217.114.8.196`. Приложение, админка, веб-версия и API работают
по новому имени; прежнее имя `sslip.io` **намеренно оставлено** — его знают
уже установленные сборки, и без него они потеряли бы связь с клубом.

**Зачем переезжали.** Приложение не работало без VPN. Причина не в сервере:
на этом же адресе живёт другой проект заказчика на домене `xtrud.pro`, и он
без VPN работает. Резали не адрес, а имя — техника блокировки по имени
соединения отбрасывает имена `sslip.io`. HTTP/2 и сжатие были включены
и до этого, так что дело было не в них.

Делается скриптом: `scripts/set-domain.sh padelmagas.ru www.padelmagas.ru`.
Он проверяет записи DNS, расширяет сертификат, добавляет имена в nginx,
переключает адрес сервера в приложении и выкладывает веб-версию.

## ⚠️ На сервере работает ЧУЖОЙ проект

С 31 августа 2026 на этой же машине развёрнут **`api.xtrud.pro`** — самостоятельно
поднятый Supabase (11 контейнеров: PostgreSQL, авторизация, хранилище, Realtime,
Edge Functions, imgproxy, пул Supavisor) плюс приложение на Next.js.

**Разделение чистое, конфликта нет:**

| Запрос | Куда идёт |
|---|---|
| `api.xtrud.pro` и `217-114-8-196.sslip.io` | Supabase чужого проекта, порт 8000 |
| `padel.217-114-8-196.sslip.io` | наш сайт по HTTPS |
| всё остальное на порт 80, включая голый IP | наш сайт по HTTP |

**Правила работы на этой машине:**
- Наши файлы живут **только** в `/var/www/padelmagas`.
- Наши конфигурации nginx — **только** `padelmagas` и `padelmagas-ssl`.
- Файл `xtrud-api` и контейнеры Supabase **не трогать никогда**.
- Перед любым изменением nginx делать резервную копию:
  `tar czf /root/nginx-backup-$(date +%F-%H%M%S).tar.gz /etc/nginx`
- После изменения обязательно `nginx -t` **до** `systemctl reload nginx`.

Резервная копия конфигурации перед добавлением HTTPS:
`/root/nginx-backup-20260901-145536.tar.gz`

Возможные варианты: отдельный VPS под наш бэкенд, либо переиспользовать уже стоящий
PostgreSQL. **ВОПРОС К ЗАКАЗЧИКУ Q34.**

## Развёртывание

Всё воспроизводится из репозитория одной командой:

```bash
SSHPASS='пароль' scripts/deploy.sh root@217.114.8.196
```

Скрипт ставит nginx, собирает страницы, копирует шрифты и картинки из `assets/`,
настраивает раздачу, выставляет права и проверяет, что страницы отвечают.
Запускается повторно без последствий.

⚠️ Скрипт создаёт конфигурацию с `default_server` на порту 80. На этой машине она уже
стоит и сосуществует с чужим проектом — при повторном запуске ничего не сломается,
но **HTTPS-конфигурацию `padelmagas-ssl` он не создаёт**, она заведена вручную и живёт
отдельно.

## Безопасность — что стоит сделать
1. **Сменить пароль root.** Он передавался в переписке.
2. **Перейти на вход по SSH-ключу** и отключить вход по паролю. На машине с чужой
   рабочей базой это не формальность.
3. Fail2ban на сервере уже включён.

## Как выкладывается API

Раньше этого не было записано нигде, и выкладка каждый раз восстанавливалась
по памяти. Записываю, как устроено на самом деле (проверено 10.10.2026).

Git на сервере **не развёрнут**. В `/opt/magas-padel` лежит:

| Что | Зачем |
|---|---|
| `api/` | копия исходников: `src`, `prisma`, `tools`, `package*.json`, `Dockerfile` |
| `docker-compose.yml` | службы `api`, `db`, `cache`; образ `magas-padel-api` собирается на месте |
| `.env` | пароль базы и ключи, среди них `SMSRU_API_ID` — **он на сервере есть** |
| `backups/`, `backup.sh` | снимки базы |

Поэтому выкладка — это синхронизация `src` и пересборка контейнера:

```bash
scripts/deploy-api.sh        # показать, что уедет, ничего не меняя
scripts/deploy-api.sh --go   # выложить
```

Скрипт сначала проверяет, что код компилируется, потом синхронизирует
исходники, пересобирает образ, ждёт `healthy` и стучится снаружи
в `https://padelmagas.ru/api/club`. Любой неуспех останавливает выкладку.

Статику (`v1/`) выкладывает `scripts/build-app.sh` — это отдельная вещь,
API она не трогает.

**Напоминание:** на этой же машине работает чужой Supabase. Выкладка трогает
только службу `magas-api`.

## Два выключателя подтверждения звонком

Их легко перепутать, а последствия разные.

| Переключатель | Что делает | Где |
|---|---|---|
| `phone_verify_on` | требует подтверждения звонком **при регистрации** | админка → «Управление» → «Приложение» |
| наличие `SMSRU_API_ID` | включает саму возможность звонка, а с ней и **возврат забытого пароля** | `.env` на сервере |

`phone_verify_on` сейчас **выключен намеренно**: в App Store лежит версия 1.0.2
(сборка 65), которая про подтверждение звонком не знает и не присылает его.
Включить его — значит сломать регистрацию всем, кто поставил приложение из
магазина. Включать можно после того, как 1.0.4 выйдет и разойдётся.

Возврат пароля от этого выключателя **не зависит** (D46): он работает, пока
задан `SMSRU_API_ID`. Старые сборки от этого не страдают — у них просто нет
кнопки «Забыли пароль?».
